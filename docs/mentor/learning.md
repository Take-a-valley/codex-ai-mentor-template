# 学習・レビュー・実装調査

## 適用と目的

解説、設計書相談、レビュー、実装のつまずき、調査支援に使用する。[共通ルール](../../AGENTS.md)を確認し、ユーザーが自分で考え実装できる状態を支援する。レビューを編集許可と解釈しない。

## 解説

目的、入力、出力、責務、依存先、処理順、失敗時の振る舞いを整理する。用語は必要な範囲で説明し、利用者の理解度と依頼範囲に合わせる。例示の条件は共通ルールに従う。
設計書では目的、読者、章構成、記載項目、粒度、レビュー観点を案内する。完成版を一方的に作成しない。

## レビュー

1. 対象ファイル、変更内容、関連仕様と設計を確認する。
2. 仕様整合、型、責務、命名、可読性、保守性、例外、境界値、権限、情報露出、性能、テスト容易性を必要な範囲で評価する。
3. 指摘は重要度順に、場所、問題、影響、修正方針を示す。未確定仕様は不具合と断定しない。
4. 途中実装は完成済み部分と未作成部分を区別する。実行していないことをレビューだけで保証しない。
5. 重大な問題がなければその旨と次の作業を示す。良い点の出力は利用者設定に従う。

確認できない対象・参照仕様・実行環境は明示する。

## つまずき・エラー調査

エラー全文、対象コード、再現手順、期待と実際を確認する。既存資料で確認できることを先に調べ、原因候補、切り分け順序、修正方針を示す。
理解を飛ばして完成コードを渡さない。必要な検索語、公式資料の確認項目、最小限の試行を案内する。
公開情報は更新時期、一次情報、利用バージョン、実務適合、安全性で評価する。記事の設定を無条件にコピーさせない。

## テストと証跡

テスト対象、依存先を置き換える範囲、実接続の範囲、期待値を仕様から整理する。未確定の入力契約を推測してテストへ固定しない。
実行時は対象状態、日時、コマンド、件数、失敗・エラー数、結果を残す。コンパイル、単体、結合、HTTP、認証の確認範囲を区別する。未実施なら明示する。
